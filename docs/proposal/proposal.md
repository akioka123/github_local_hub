# github_local_hub 企画案

- 作成日: 2026-10-04 (Asia/Tokyo)
- 対象: 個人用・非収益化
- 現在地: ゲート1の承認待ち
- この文書は初期化の範囲を確認するための企画案。技術案と暫定の範囲は、要件確認・基本設計で確定する。

## 目的

GitHub の Issue と PR を確認する手間を減らす。issue-* / pr-* 系の開発支援スキルが付けるラベルで対象を絞り込み、状況確認からコメント返却までを個人用の画面で行う。

## ユーザーが指定した条件

- 開発の省力化が目的で、当面は個人用。
- ローカルで動作し、Docker で起動する。
- 必要なデータを DB に保存する。
- コンテナを削除しても復旧できるよう、作業時にバックアップを随時更新する。
- Codex と Claude Code の両方から開発を継続できる構成にする。

## 初版の範囲案

| 機能 | 初版の案 |
|---|---|
| 対象リポジトリ | 利用者が登録した複数の GitHub リポジトリを一覧で扱う |
| 状況確認 | Issue / PR の種別、open / closed / merged、ラベル、更新日時、関連リンクを表示する |
| 絞り込み | リポジトリ・種別・状態・ラベルで絞る。初期プリセットに加え、取得した任意のラベルを選択できる |
| 詳細表示 | 本文と通常コメントの履歴を確認し、必要に応じて GitHub の元画面を開く |
| コメント返却 | Markdown の下書きを DB に保存し、対象リポジトリ・番号・本文を画面で確認して、利用者の送信操作で投稿する |
| GitHub 同期 | 手動更新を必須にし、最終同期日時と失敗を表示する。失敗時は前回取得したデータを古いデータとして表示する |
| ローカル保存 | 取得済みデータ、登録リポジトリ、フィルター設定、下書き、送信結果を保存する |
| バックアップ | DB の更新成功後に、ホスト側の最新バックアップを更新する |

「コメント返却」は通常の Issue / PR コメントを初版の案とする。PR の行単位コメント・Approve / Request changes、ラベル変更、定期同期は、ゲート1承認後の要件確認で必要性を決める。

## スキルで使われるラベル

参照元は `~/.claude/skills/issue-report/SKILL.md`、`issue-work/SKILL.md`、`pr-watch/SKILL.md`、`issue-flow-loop/SKILL.md` と `~/.claude/scripts/issue-flow.mjs`。ここでは仕様確認のために参照した。スキルやループを実行するものではない。

| 分類 | 確認したラベル |
|---|---|
| Issue の状態 | `status:triage`, `status:ready`, `status:in-progress`, `status:needs-info`, `status:needs-human`, `status:blocked` |
| PR の差し戻し | `pr:needs-fix` |
| 種別 | `type:bug`, `type:balance`, `type:data`, `type:docs`, `type:infra` |
| 優先度 | `p1`, `p2`, `p3` |

`status:needs-human` は導入時の標準ラベル一覧にはないが、ループの運用で使われるため候補に含める。Issue / PR の実際の GitHub 状態とラベルは別の情報として表示する。上記ラベルが存在しないリポジトリも扱えるようにする。

## 実現方法の比較

| 方式 | 利点 | 負担 | 判断 |
|---|---|---|---|
| Docker + ローカル Web アプリ | 一覧・本文・コメントを同じ画面で扱え、ブラウザから使える | ローカルの HTTP サーバーが必要 | 推奨 |
| CLI / TUI | 構成を小さくできる | 複数対象の見比べと長文コメントの編集に制約がある | 今回は採用しない案 |
| デスクトップアプリ | 専用ウィンドウで使える | Docker に加えてアプリの配布・更新の仕組みが必要 | 今回は採用しない案 |

## 技術・運用の方向性

- Docker Compose でローカル Web アプリを起動する。ホストの待受は `127.0.0.1` に限定する。
- DB は SQLite を第一候補にする。個人利用を前提に、独立した DB サーバーの管理を増やさない。
- GitHub を Issue / PR / コメントの正本とし、ローカル DB は取得済みデータとアプリ固有データを保持する。
- GitHub 連携はサーバー側の REST API を第一候補にする。取得と投稿に必要な対象・権限だけを設定する。
- 認証情報は実行時の設定として渡し、ブラウザ・DB・バックアップ・Git に保存しない。認証方式は要件確認で決める。
- フロントエンド・サーバーの言語とフレームワークは基本設計で選定する。

## 保存とバックアップ

- `data/` をホストからコンテナへマウントし、DB 本体を置く。
- `backups/` も別のホストディレクトリとしてマウントし、最新のバックアップを置く。両方を Git の追跡対象から外す。
- 同期、設定・下書きの保存、送信結果の記録など、DB の更新が成功した時点でバックアップを更新する。更新が集中するときの集約方法と最大遅延は非機能要件で定める。
- 使用中の DB ファイルの単純コピーは避け、SQLite のバックアップ API 等で整合性のあるスナップショットを一時ファイルへ作る。完了後に同じバックアップディレクトリ内で最新ファイルを置き換える。
- 作成に失敗したときは前回の成功したバックアップを残し、バックアップ失敗を画面に表示する。DB 更新の成否とは区別する。
- コンテナ削除・再作成時はホストの DB を再利用する。DB を失った場合は、アプリを停止して最新バックアップから明示的に復元する。DB の異常時に自動で空の DB に置き換えない。
- バックアップは利用者の想定どおり最新1件を上書きする方式とする。上書き前の履歴保存と別媒体への複製は初版の範囲案に含めない。同じホストのディスク故障まで復旧できる構成ではない。

## Codex / Claude Code からの開発

- `AGENTS.md` にプロジェクトの概要・制約・工程・確定後の起動と検証の手順を集約する。
- `CLAUDE.md` に `@AGENTS.md` を記載し、Claude Code が共通規約を読み込めるようにする。
- 現在地は `docs/gates/gate-status.md` に記録し、両方のエージェントで同じものを参照する。
- プロジェクト固有の設定は `.claude/` に置く。グローバル共通スキルをコピーしない。個人設定とワークツリーは Git 追跡から外す。
- 個人の絶対パス、Codex の画面操作ツール、特定エージェントだけの機能をアプリの起動要件にしない。

## コストと運用時間

追加の有料サービスを導入せず、追加の初期サービス費・月額サービス費は各0円とする案。既存 PC、ネットワーク、GitHub と Docker の利用環境を使う。これはユーザーが指定した予算上限ではなく、企画案の制約である。

定常運用に必要な手作業は週30分以内を目標案にする。アプリを使う開発作業の時間と、障害対応・初期開発は含めない。金額・時間の変更が必要になった場合は、要件に反映する前に確認する。

## 初版では行わないこと

- 他の利用者向けの提供、収益化、外部サーバーへの公開。
- アプリからの自動コメント投稿、PR の自動承認・マージ、スキルや開発エージェントの起動。
- 本アプリが接続先リポジトリのラベルを自動作成・自動変更すること。

## 次工程で確認すること

1. 対象リポジトリの登録方法と件数、private リポジトリの有無、認証方式。
2. ラベルの複数選択を AND / OR のどちらで扱うか、保存フィルターと優先表示の要否。
3. コメント返却の範囲、ラベル変更や正式な PR レビューの要否。
4. 手動・定期同期の範囲、表示する PR 情報と関連 Issue の扱い。
5. バックアップ更新の最大遅延と、復元手順・検証方法。
6. 追加サービス費0円、定常運用週30分以内という目標案の調整。
