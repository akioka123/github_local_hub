# MVP要件

2026-10-05 (Asia/Tokyo)。企画案を基に、ユーザーの「現行計画に従って開発を開始。MVPの開発終了まで実行」を開発継続の承認として扱う。各工程での再承認待ちは行わない。以下の未指定部分は実装判断であり、ユーザーの指定条件とは区別する。

## 利用シナリオと受入条件

1. `owner/repository` を入力して複数の公開・非公開リポジトリを登録できる。未同期の登録状態もDBに保存する。
2. 手動で1件または全件を更新できる。Issue/PR、open/closed/merged、タイトル、本文、任意ラベル、著者、更新日時、通常コメントを取得する。全ページを取得してからリポジトリ単位で一括保存する。
3. リポジトリ・種別・状態・複数ラベルで絞り込む。複数ラベルはOR、異なる項目間はAND。標準のスキル用ラベルと取得した独自ラベルを選択できる。最後の条件を保存する。
4. 一覧から本文・通常コメントを表示し、GitHubの元画面を開ける。Markdownはソースをそのまま安全に表示し、HTMLや外部画像は実行・取得しない。
5. Markdown下書きを入力停止後800msまたは明示保存でDBに保存する。失敗を表示し、未保存のまま画面を閉じる際はブラウザに警告を要求する。下書き保存を完了してから対象を切り替える。
6. リポジトリ、番号、タイトル、本文を確認するダイアログから通常コメントを送信できる。自動投稿、ラベル変更、正式レビュー、行コメント、マージは行わない。
7. 送信IDをDBに先に記録し、同じIDの再要求で二重投稿しない。結果不明なら再投稿をブロックする。非表示Markdownマーカーによる同期照合、または利用者がGitHubで確認後の明示解除を行う。マーカーは完全なGitHub側冪等性を保証するものではない。
8. 同期失敗時は前回のデータと同期日時を保持し、失敗表示を出す。リポジトリごとの成功・失敗を扱う。定期同期・Webhookは範囲外。
9. DB更新ごとに同期的にSQLite backup APIで整合性のある最新1件を更新する。成功時のみ一時ファイルを置換。失敗時は前回バックアップを残し、画面で警告・手動再試行を提供する。DB保存とバックアップ成否は別々に扱う。
10. コンテナ再作成時にホストのDBを利用する。DB喪失時は停止して検査済みバックアップから明示復元できる。破損時は起動を停止し、自動初期化しない。

## 実装上の選択と非機能要件

- Python 3.12の標準ライブラリとSQLite、素のHTML/CSS/JavaScript。追加パッケージ・有料サービスなし。フレームワークのビルドやDBサーバーは不要。
- Docker Composeでホストの `127.0.0.1` のみ公開。個人用、単一プロセス。アプリのデータ用ファイルロックで二重起動と起動中の復元を拒否する。
- `GITHUB_TOKEN` は環境変数で渡すfine-grained PAT。対象リポジトリにMetadata read、Issues read/write、Pull requests read。読み取りだけならIssues readでよい。公開リポジトリは未認証でも取得可能だがAPI上限が低い。
- トークンをブラウザ・DB・バックアップ・ログへ返さない。GitHubエラー本文は保存せず安全なエラーへ置換する。
- Host検査、同一Origin検査、JSONと専用リクエストヘッダー、CSPで別サイトからのローカル操作を防ぐ。端末上の別プロセスに対するユーザー認証は提供しない。
- GitHub通信は1要求30秒タイムアウト、各一覧は100件/ページ、上限1,000ページ。同期・投稿は直列化する。大規模リポジトリでは全通常コメント取得の時間・API使用量が増える。
- 通常コメントのみ表示。レビュー・差分・CI・関連Issueの自動抽出・通知・リポジトリ削除・検索文字列・保存フィルターの複数プリセットは将来対応。
- 同一ホストの `data/` と `backups/` を使う。最新1件なのでディスク故障や過去時点への復元は対象外。
- サービス費の追加0円、定常管理週30分以内を設計上の目標として継承。実際の利用時間は未測定。
- GitHub実データへの書き込みテストは行わない。単体・HTTP結合・模擬GitHubとの一連操作・復元で検証し、Dockerと実GitHubの検証状況を別途報告する。
